# GetBuggy — Standing Rules

These rules apply to every session working in this repository. They come from the founders and do not get relaxed without them explicitly changing this file.

- Read `PROJECT_STATUS.md` and `PLAN.md` at the start of every session. Update them; never contradict them.
- Run the regression harness before every commit that touches checks or the crawler. If baselines change, explain why in the commit message.
- Every push to `main` deploys to Render automatically. After every push, run `post_deploy_check.py` against the live URL and confirm `/version` and `/health` both check out. Log each deploy in `PROJECT_STATUS.md`.
- Real form submission stays off by default. Never enable it. Never add a code path that submits a real form without an explicit, per-run opt-in flag that defaults to false.
- Security checks are passive and read-only: observe responses, headers, and loaded resources. No payloads, no fuzzing, no login attempts, no port scans, no exploitation. The only active probes allowed are GET requests to a fixed endpoint list, run only against the URL the user pasted.
- Security findings are ownership-gated. Public reports show them at category level only ("a possible exposure was found — verify you own this site to see details"). Full detail renders only when the server flag `GETBUGGY_SHOW_SECURITY_DETAILS=true` is set, and never on a shareable permalink or export.
- SSRF protection applies to every new fetch. Any code that requests a URL derived from site content goes through the existing SSRF guard.
- Time budget: the 60-second timeout is per page. A crawl runs as a background job with a hard cap of 6 minutes; on cap, return a partial report. Within one crawl, pages load concurrently up to `CRAWL_CONCURRENCY` (an env var, tunable on Render without a deploy — see `PROJECT_STATUS.md` for the current value and why; lowered from 3 after real live-crawl capacity incidents, see Known Issues). The server-level concurrency cap of 2 runs stays. Expensive checks must be skippable, with the skip recorded in the report.
- Memory guards on the crawl process must be based on measuring real memory usage (RSS/aggregate process-tree usage), not virtual-address-space limits like `RLIMIT_AS` — confirmed 2026-09-18 that `RLIMIT_AS` is incompatible with Playwright's Node.js driver (V8 reserves large virtual address space on startup regardless of actual physical usage, so any limit tight enough to matter breaks every check outright, not just heavy ones). Any such guard needs a real Linux test before it's trusted, not just local dev — this exact incompatibility didn't (and structurally couldn't) show up when tested on macOS, since macOS doesn't support lowering `RLIMIT_AS` at all.
- Anything that changes how the browser launches (Playwright/Chromium launch args, resource limits applied to it, process/session setup) gets a local Docker run — matching the actual deployed Linux environment — before it's pushed, not just local dev on whatever OS this happens to be running on.
- The site is public with no login — every run must be rate-limited (per-IP and a daily global cap on browser runs, both configurable via env var, see `PROJECT_STATUS.md` for current values) and requires the "I own this site or have permission to check it" authorization checkbox, enforced both client- and server-side. A rejection is a plain-English message, never a bare status code.
- CI runs unit tests and the fixture-based regression harness (`--skip-live`) on every push and pull request. Live-site baselines (`medvi.org`) only run on a schedule or manual dispatch — never on every push, so CI can't flap on real-world site drift or network conditions.
- Funnel/analytics logging counts events, never tracks individual visitors — no cookies, no session/user IDs, nothing that lets one log line be tied to another from the same visitor. A raw URL or email address never appears in a funnel log line itself.
- Error tracking (Sentry) is no-op unless `SENTRY_DSN` is set in the environment — never add a dependency or code path that phones home by default.
- Speed findings must reflect the site, not our server. Anything derived from our own render time is `needs_look` unless calibrated against a reference page.
- Plain English in every user-facing string. Assume the reader owns a bakery and has never opened developer tools. Every finding says: what's wrong, why it matters to them, how to fix it, who fixes it (you / your web person / your host / your lawyer).
- Never fabricate. If a check could not run, say so in the report. "Couldn't verify" beats a guessed result.
- Small commits with descriptive messages. Push at the end of each step after the harness passes.
- Decisions: cookie-compliance copy defaults to US with a `jurisdiction` field; report retention is 30 days; free tier checks 5 pages per crawl, Pro checks 10+ (`DEFAULT_CRAWL_PAGE_CAP` in `core.py` — keep it configurable, never hardcode a page count elsewhere). Decide everything else autonomously and record each decision in `PLAN.md`. If a decided item seems wrong, say so in the summary; do not block on it.
- Do not build accounts, Stripe, the Pro tier, scheduled re-checks, third-party widget checks, competitor comparison, or anything from product Phases 2–4 in `PLAN.md`. Those wait until after the ten-business test.
- Every step ends with a summary containing: what shipped, the harness output (actual, pasted), live-site verification (actual `/version` and a real check through the live URL), what was skipped and why, and any decision the founders should know about.
