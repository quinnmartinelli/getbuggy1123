## 1. Overview

This is a small website QA tool called "website-checker" (product name: **GetBuggy**). You point it at a URL (or a local HTML file) and it crawls the site — not just the one page — opening each page in a real (headless) browser, watching what happens, and reporting problems it finds per page: broken links, missing images, JavaScript errors, slow load times, images missing accessibility text, forms that silently fail to submit, mobile layout/readability problems, SEO basics, and Core Web Vitals. It's meant as a quick automated "does this site have obvious problems" check, not a full test suite.

There are now two ways to use it:

1. **Command line** (for local testing):
   ```
   python checker.py test_page.html              # single page
   python checker.py https://example.com          # single page
   python checker.py --crawl https://example.com   # whole site (sitemap.xml, capped at DEFAULT_CRAWL_PAGE_CAP pages — 5 by default, free-tier limit)
   ```
   Prints a report grouped by severity (High / Medium / Low); `--crawl` groups by page first.

2. **Web app** (in progress — being built so anyone can use it without installing anything): a small server (`server.py`) exposes a `/api/check` endpoint — which now always does a **whole-site crawl**, not just the submitted page, capped at `CRAWL_PAGE_CAP` pages (5 by default — the free-tier limit; Pro raises this to 10+, see `PLAN.md`'s pricing table) — and a one-page frontend (`static/index.html`) lets someone paste a URL into a box and see the report — a deduplicated list of problems (the same issue recurring across pages is shown once, with "Found on: N pages" — see `core.py`'s `dedupe_site_problems`, Step 5) and a summary line ("Checked 5 of 37 pages — 6 problems on 3 pages. Checking more pages is coming with Pro.") — in a browser. This is what's being prepared for deployment so businesses can use it directly — see the Deployment section once that's live.

   **Running it locally, for development:** always start it with `--reload`, not just `uvicorn server:app`:
   ```
   source venv/bin/activate
   uvicorn server:app --host 127.0.0.1 --port 8000 --reload
   ```
   Without `--reload`, the server loads `core.py`/`server.py` into memory once at startup and keeps serving that version even after the files on disk change — see the 2026-09-16 Progress Log entry for what that actually cost us. `--reload` makes it restart itself automatically whenever those files change.

**Key dependencies (installed in the venv):**
- **`requests` (2.34.2)** — used to check whether links (both on-page `<a href>` links and some image/network checks) return a working HTTP response, without needing a full browser for that part.
- **`playwright` (1.63.0)** — drives a real headless Chromium browser so the checker can load the page like a real visitor would, and listen for console errors, crashed scripts, failed network requests, and slow loads. This is the core of how the tool works.
- **`fastapi` (0.141.1)** — the web framework behind the new `/api/check` endpoint, so the checker can be triggered over the internet instead of only from the command line.
- **`uvicorn[standard]` (0.53.0)** — the program that actually runs the FastAPI app and listens for incoming web requests.
- Supporting libraries pulled in automatically: `certifi`, `charset_normalizer`, `greenlet`, `idna`, `pyee`, `typing_extensions`, `urllib3`, plus FastAPI/uvicorn's own sub-dependencies (`starlette`, `pydantic`, `click`, `h11`, etc.).

`requirements.txt` records the exact versions installed for all direct dependencies, so the environment (or a Docker image — see Deployment) can be rebuilt from scratch without guessing.

## 3. Architecture

### Module layout

| Module | Role |
|---|---|
| `core.py` | The checking engine. Owns SSRF protection (`validate_public_url`), the per-page check pipeline (`_check_single_page`), the whole-site crawl (`run_site_check`) and its single-page counterpart (`run_check`), and shared helpers (`sort_problems`, `summarize_site_check`). Imports `checks_seo.py` and `checks_performance.py` as plugged-in check modules. |
| `checks_seo.py` | Self-contained SEO/basic-security checks (title, meta description, H1, favicon, mixed content). No dependency on `core.py`, to avoid a circular import. |
| `checks_performance.py` | Self-contained Core Web Vitals check (LCP, CLS). Also import-free of `core.py`, for the same reason. |
| `checker.py` | CLI entry point. Calls `run_check`/`run_site_check` directly, in-process — no server, no job queue. |
| `server.py` | FastAPI app. Turns a check into an async background job (see below), plus `/version`, `/api/early-access`, `/privacy`, `/terms`, and serves `static/`. |
| `report_store.py` | Saved reports, 30-day retention, in MongoDB. Off unless `MONGODB_URI` is set. `save_report` (called when a job finishes) never raises; `get_report` backs `/api/check-status` once a job has left memory. |
| `run_site_check_subprocess.py` | Thin CLI wrapper around `run_site_check()`, invoked by `server.py` as a subprocess so a runaway crawl (and its Chromium child) can be `SIGKILL`ed as a whole process group. Streams `META`, `PAGE`, `PROGRESS <completed> <total>` lines and a final `RESULT <json>` line over stdout. Its `RLIMIT_AS` memory ceiling is off by default (`CRAWL_SUBPROCESS_MEMORY_LIMIT_MB=0`, see the 2026-09-18 incident); a `MemoryError` is caught and reported as a clean message rather than a traceback. |
| `render_markdown.py` | Hand-rolled minimal markdown renderer, used only to render `legal/*.md` for `/privacy` and `/terms`. |
| `static/index.html` | The landing page + frontend. Submits to `/api/check`, polls `/api/check-status/{job_id}`, renders the per-page/per-severity report client-side. |
| `regression_check.py` | Pre-deploy sanity check. Calls `run_check`/`run_site_check` in-process (bypasses `server.py` entirely) against a fixed target list and diffs problem *categories* (and, for the crawl target, page-discovery counts) against known-good baselines. |

| `Dockerfile` | `python:3.12-slim` + `playwright install --with-deps chromium` + the app, run via `uvicorn`. What Render builds and deploys. |

### How a check plugs in

Every check function takes the shared, in-progress `problems` list and appends plain-English finding dicts to it — it never returns a report of its own. Two shapes exist, depending on whether the check needs a fresh page load:

- **DOM-only checks** (e.g. `checks_seo.check_seo_and_security`) take the already-loaded main `page` object and `problems`, and run directly against the page `_check_single_page` already navigated to. They add no extra page loads.
- **Fresh-navigation checks** (e.g. `checks_performance.check_core_web_vitals`, `core.check_mobile_responsiveness`) take the `browser`, the target `url`, `timeout_ms`, and `problems`, and open their own `browser.new_page()` — because they need to observe something (Core Web Vitals timing, a phone-width viewport) that the main page's already-completed load can't give them after the fact.

Both shapes wrap their own logic in `try/except` internally, so one check failing on an unusual page can't take down the others or the rest of that page's checks. A check module keeps its own local `HIGH`/`MEDIUM`/`LOW` constants rather than importing them from `core.py`, since `core.py` imports the check modules (importing back would be circular).

`core.py`'s `_check_single_page()` is where checks are wired in — it calls each one in sequence against one already-open browser. To add a new check: write a function matching one of the two shapes above, add it to `_check_single_page()`, and (if it's genuinely a new problem type) add its category to `regression_check.py`'s baselines with a comment explaining why the count is what it is.

### How a finding flows to the report

1. A check appends `{"category": str, "message": <plain-English string>, "severity": HIGH|MEDIUM|LOW, "confidence": VERIFIED|NEEDS_LOOK}` to the shared `problems` list. `category` is the stable identifier (regression baselines compare *this*, not the message text, since message text can legitimately vary run to run); `message` is the full plain-English explanation shown to the user; `confidence` (added GetBuggy Step 2, 2026-09-17) is independent of `severity` — see the Fixed entry below for what each check was assigned and why.

   Some things a check tries to look at genuinely can't be observed at all — not "found something, unsure if it's real" (that's `confidence: needs_look` on a normal finding), but "there is no finding here either way": a link needing a login (401), a link still bot-blocked even after the browser recheck, a request that timed out, or an expensive per-page check that couldn't finish in time. These go in a separate `could_not_check` list (plain-English strings, not categorized/severity'd findings) alongside `problems`, added GetBuggy Step 2.
2. **Single page:** `run_check()` returns `(problems, could_not_check)`.
   **Whole site:** `run_site_check()` discovers candidate pages (sitemap.xml, falling back to homepage links), filters them through `robots.txt` and `validate_public_url`, caps the result at `page_cap`, and checks up to `CRAWL_CONCURRENCY` pages at once via a thread pool (env var; code default 1, set to 2 on Render — see the 2026-09-18 incident) — each page gets its own standalone browser launch (`_check_page_standalone`). Results come back as `{"pages_found_total", "pages_checked", "used_sitemap", "pages": [{"url", "problems", "could_not_check"}, ...]}`.
3. `sort_problems()` orders a page's problems HIGH → MEDIUM → LOW for display. This is presentation only; it plays no part in what regression baselines check.
4. `server.py`'s `POST /api/check` does not run the crawl inline (a crawl can take minutes — far too long for one HTTP request/response). It takes a concurrency-limited slot (`MAX_CONCURRENT_CHECKS`, a `threading.BoundedSemaphore`), spawns `run_site_check_subprocess.py` as its own OS process in its own process group, and returns a `job_id` immediately. A background thread reads that subprocess's `PROGRESS`/`RESULT` lines off stdout into an in-memory `_jobs` dict; a watchdog thread `SIGKILL`s the whole process group (Chromium child included) if it runs past `CRAWL_TIMEOUT_SECONDS`.
5. The frontend polls `GET /api/check-status/{job_id}` until `status` is `"done"` or `"error"`, then renders `summarize_site_check()`'s plain-English summary line, each page's problems grouped by severity (with a "Needs a look" badge on any `confidence: needs_look` finding, in whichever severity group it's in), and a "What we couldn't check" section per page for that page's `could_not_check` notes.
6. `checker.py` and `regression_check.py` skip the job-queue/subprocess machinery entirely — they call `run_check()`/`run_site_check()` directly in-process. The job queue exists only to make a slow check fit inside an HTTP request/response cycle in `server.py`; it isn't part of the checking engine itself.

**Note (2026-09-17):** `CRAWL_TIMEOUT_SECONDS` now defaults to a flat `360` (6 minutes), matching `CLAUDE.md`'s standing rule — it's a promise about the user's maximum wait, not a per-page budget, so it deliberately does not scale with `CRAWL_PAGE_CAP` (it used to be `CRAWL_PAGE_CAP * 45`). **Closed in Step 4 (2026-09-21):** the worker now streams `META` (what was found/selected/skipped, site-wide findings) and one `PAGE` line per finished page, so when the watchdog kills the crawl at the cap, `server.build_partial_result` returns everything gathered as a normal report marked `partial: true` ("Partial report — N of M pages checked before the 6-minute time limit", unfinished pages listed). A worker that dies mid-crawl (e.g. killed by the host) after some pages finished is handled the same way. Only a crawl that produced nothing at all is still a plain error.

Root cause: `RLIMIT_AS` caps *virtual address space*, not physical memory in use. Playwright's Python client launches its own Node.js driver subprocess to talk to the browser, and V8 (Node's JS engine) speculatively reserves a large amount of virtual address space on startup regardless of how much it actually uses — it hit the 1.2GB ceiling before a single page was ever checked. ## 7. Regression Testing (new, 2026-09-16)

`regression_check.py` is a standalone pre-deploy sanity check: it runs `core.run_check()` (in the default, safe environment — it unsets `ENABLE_REAL_FORM_SUBMISSION` itself) against a fixed list of targets and compares the set/count of problem *categories* returned against a known-good expected result for each, printing a PASS/FAIL with a diff (missing vs. unexpected categories) per target. `could_not_check` entries aren't compared at all — only counted for visibility in the PASS line. Targets live in a simple, extensible `TARGETS` list at the top of the file — add more there as the project grows. Three target `"mode"`s exist: plain (`run_target`, the default — `core.run_check()` against a local file or live URL), `"crawl"` (`run_crawl_target` — `core.run_site_check()` against a local HTTP server serving `test_site/`), and `"embedded_form"` (`run_embedded_form_target` — `core.run_check()` against a local file whose iframe points at a local HTTP server serving `test_site_embedded/`, with `GETBUGGY_TEST_EMBEDDED_PROVIDER_HOST` set so it's recognized as a stand-in provider). As of 2026-09-17 it covers 7 targets: `test_page.html`, the four form-check-accuracy fixtures (`test_page_wizard.html`, `test_page_form_triggers.html`, `test_page_form_validation.html`, `test_page_iframe_form.html`), `http://medvi.org` (a live external site, expected to be near-clean; flagged in-file as subject to real-world drift/network flakiness outside this codebase's control), and the `test_site/` crawl fixture. Exits 0 only if every target passes.

**Timing-tolerant categories (added GetBuggy Step 2, 2026-09-17):** `TIMING_TOLERANT_CATEGORIES` in `regression_check.py` lists every timing/perf-driven category (`Page Load Time`, `Largest Contentful Paint`, `Layout Shifts While Loading`, `Slow Server Response`, `Heavy Page`, `Many Requests`, `Oversized Images`) with a numeric tolerance band — `diff_report()` treats any deviation within that band (from whatever count, usually 0, a target's `expected_categories` implies) as a total non-event, and any deviation past it as a note, never a failure, regardless of which target it's on. This is separate from and more general than the older per-target `flaky_categories` mechanism (still used for `medvi.org`'s occasional live-network `Broken Link` timeout), which only tolerates a specific category on a specific target. Structural findings (broken link, missing title, missing alt text, etc.) are deliberately *not* in this set and are still compared exactly everywhere.

Run it before every deploy with:

```
source venv/bin/activate
python regression_check.py
```

**CI (added GetBuggy Step 3, 2026-09-19):** `.github/workflows/ci.yml` runs `pytest tests/` and `python regression_check.py --skip-live` automatically on every push to `main` and every pull request — `--skip-live` excludes any target marked `"live": True` (currently just `medvi.org`), so CI never flaps on live-network conditions or the site's own content changing. `.github/workflows/live-regression.yml` runs the full, unfiltered harness (including `medvi.org`) on a daily schedule plus manual dispatch — the only place the live target actually runs automatically.

## 8. Operational Safety (new, GetBuggy Step 3, 2026-09-19)

**Rate limiting.** `server.py`, both in-memory, both rolling windows (not fixed clock buckets):
- Per-IP: `RATE_LIMIT_PER_IP_PER_HOUR` env var, default `5` per rolling 60 minutes.
- Daily global cap on browser runs: `DAILY_GLOBAL_RUN_CAP` env var, default `200` per rolling 24 hours — checked first, since it protects everyone, not just one caller.

Both reset on a restart/redeploy (no database yet) — an accepted gap for a cost guard, not a security control. Real client IP comes from `X-Forwarded-For` (Render proxies every request), falling back to the raw connection for local dev. Rejections are HTTP 429 with an actual plain-English message explaining what happened and what to do, not a bare 429.

**Authorization checkbox.** "I own this site or have permission to check it" — required client-side (native HTML5 validation blocks the form from submitting at all until it's checked) and independently required server-side (`POST /api/check` rejects with a 400 if `authorized` isn't `true`, since client-side validation doesn't stop a direct API call). Recorded with the run in the in-memory job record.

**`GET /health` — point an external uptime monitor here, not (only) `/version`.** `/version` only proves the server *process* is alive; `/health` actually launches and closes a real headless Chromium instance in its own subprocess, so it also catches "the process is up but Chromium can't actually launch" (a broken deploy/Docker image, missing OS deps) — the failure mode that matters most for this specific tool, since every check depends on a real browser.
- URL: `https://website-checker-lrmn.onrender.com/health`
- Healthy: `200 {"status": "ok"}`
- Unhealthy: `503` with a plain-English `detail` (browser couldn't launch, or the check itself timed out after `HEALTH_CHECK_TIMEOUT_SECONDS`, default 20s)
- Suggested monitor interval: every 1-5 minutes is plenty for an uptime check; each check is a real (if minimal — launch, then immediately close, no page navigation) Chromium launch, so avoid polling much more frequently than that for no operational benefit.
- Already wired into `post_deploy_check.py`, run right after `/version` on every deploy.

**Error tracking.** [Sentry](https://sentry.io) via `sentry-sdk`, initialized only if `SENTRY_DSN` is set (checked once, at import time in `server.py`) — completely no-op otherwise, no network calls, no overhead. **Env var to set in Render: `SENTRY_DSN`.** Not yet set on the live deploy as of this writing — the founders need to create a Sentry project and add the DSN to Render's environment variables for this to actually start reporting.

**Funnel events.** Three grep-able lines on stderr (Render captures stdout/stderr as logs) — counts, not per-visitor tracking (no cookies, no session/user IDs):
```
FUNNEL url_pasted
FUNNEL report_viewed job=<job_id>
FUNNEL email_captured
```
Read conversion from Render's log search/export: count each line type over a time window (`url_pasted` → `report_viewed` → `email_captured`). `url_pasted` fires on every well-formed, safety-checked `POST /api/check`, before the authorization/rate-limit gates — genuine top-of-funnel intent, not just successful starts. `report_viewed` is logged server-side when a crawl job finishes successfully (an approximation of "the visitor's browser actually rendered it" — more robust than a frontend beacon, which silently fails from ad blockers or a closed tab). `email_captured` fires on a successful `/api/early-access` signup (the email address itself is only in the separate, already-existing CSV/notification-email record, never in this log line).

## 10. Reports: score, permalinks, retention and deletion (Step 8, 2026-10-11)

What the privacy policy has to match. The score formula and severity rubric are in `PLAN.md` ("Report score and severity rubric").

**What a report contains.** The URL checked, when, the findings (with the pages they were on, short evidence such as a link address or an error message, masked where it looks like a key), the score, and what couldn't be checked. Nothing about the visitor: no IP address, no cookie, no account. No page HTML, screenshots or crawled page content is stored, only the findings.

**Where it lives and for how long.**
- *In memory* on the server while the check runs and for 30 minutes after (`JOB_TTL_SECONDS`), or until a restart.
- *In MongoDB* (only where `MONGODB_URI` is set) for 30 days from when it was made (`report_store.REPORT_RETENTION_DAYS`, a constant on purpose, not an env var).

**Deletion after 30 days — two mechanisms, so it never rests on one:**
1. MongoDB's TTL index on `created_at` (`expireAfterSeconds` = 30 days; MongoDB's sweep runs about once a minute).
2. The deletion job `report_store.purge_expired()`: `delete_many` on everything older than 30 days. `server.py` runs it at startup and then every `REPORT_PURGE_INTERVAL_SECONDS` (default 3600 = hourly); it also drops finished in-memory jobs past 30 minutes. By hand: `python report_store.py purge`. Logs only a count (`REPORT_STORE purged N report(s)…`), never a URL.
3. Reads never return a report older than 30 days, even in the gap before either runs.

**Permalinks.** Each report gets `/r/<report_id>`, where `report_id` is a separate random 128-bit token (`secrets.token_urlsafe(16)`), not the job id. Anyone with the link can open the report without logging in until it's deleted. It always shows the public, ownership-gated version — security details never, whatever `GETBUGGY_SHOW_SECURITY_DETAILS` says — and so does the export (`/api/report/<id>/export`). There's no listing of reports and no link between a report and the one before it (a re-check copies only the previous score and date). Without `MONGODB_URI`, a permalink only works for the 30 minutes the report is in memory; after that it says the report has expired.

**Queue.** At `MAX_CONCURRENT_CHECKS` (2), new checks wait in an in-memory line of up to `MAX_QUEUE_LENGTH` (env var, default 10) and start by themselves; the page shows the place in line and a rough wait. Past that, a plain-English "very busy, try again in a few minutes". Queued checks count against the per-IP and daily limits when accepted.

**Env vars added in Step 8** (all optional): `MAX_QUEUE_LENGTH` (10), `REPORT_PURGE_INTERVAL_SECONDS` (3600).
