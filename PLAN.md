# GetBuggy — Plan

## What GetBuggy is

A tool that tells a non-technical business owner what's broken on their website, in plain English, without a developer. It grows in four phases:

- **Phase 1 (now):** You put in your URL, GetBuggy identifies every bug on the site and generates a plain-English report. No login, no install, free tier checks up to 5 pages per crawl (see the pricing table below — Pro raises this to 10+). This is the whole product until it's trusted.
- **Phase 2 (after paying customers):** Plug in. The business installs GetBuggy — a one-line JavaScript snippet first, then Shopify/WordPress apps, then Squarespace/Wix/Webflow — so it sees real visitor errors, checks the whole site on a schedule, and alerts when something breaks.
- **Phase 3 (once fixes can be verified):** Deploy agents. GetBuggy reads the business (platform, pages, visitor behavior, what keeps failing) and composes a roster of specialist agents for it — forms, checkout, booking, SEO, accessibility, performance, images, links, widgets. Agents fix only what their plug-in access allows, with the owner's permission, and every fix is re-checked.
- **Phase 4:** Keep fixed. Every verified fix is training signal; agents and rosters improve with each business. No custom model training until Phase 3 has produced thousands of verified fix-and-recheck pairs.

**Rule:** no phase starts until the previous one is trusted by paying users. The site and the report only describe what the checker can prove.

## Report score and severity rubric (Step 8)

**Severity rubric** — what every check's fixed severity means:

- **HIGH** — actively losing customers, money or search visibility, or a security exposure. *Examples:* a form that does nothing when sent, a confirmed broken internal link, the site blocked from Google, an exposed file or secret key, no HTTPS, a broken certificate.
- **MEDIUM** — a degraded experience or a compliance signal. *Examples:* a page wider than a phone screen, unlabelled form fields, low-contrast text, tracking with no consent banner, a missing page title.
- **LOW** — polish and best practice. *Examples:* missing alt text, no meta description, a missing favicon, a redirect chain, a missing security header.

Severity says how bad it would be *if true*; `confidence` (`verified` / `needs_look`) says how sure the check is. They're independent.

**Score (0–100), formula version 1** — the constants live in `report.py` (`SEVERITY_POINTS`, `AREA_CAP_POINTS`, `SCORE_BANDS`); this is a copy, not the source:

1. Start at **100**.
2. Take every *distinct* finding in the report — the deduplicated list plus the site-wide findings, so one problem on five pages counts once.
3. Leave out anything `needs_look` (we're not sure it's real) and informational notes ("Embedded form … loads correctly").
4. Each remaining finding takes off **15** (HIGH), **5** (MEDIUM) or **1** (LOW) from its report area.
5. Each area takes off at most **25**, so one bad area can't zero the score. Areas: Links and pages, Forms, Errors and broken files, Speed, Mobile, Search engines, Accessibility, Security, Site setup — plus any newer check's own `topic` (Step 7's "Cookies"). Security and accessibility findings are placed by their `group`/`topic` field, everything else by `finding_guide.GUIDE`.
6. Score = 100 − the capped area deductions, never below 0.
7. Bands: 90+ "In good shape", 75–89 "A few things to fix", 50–74 "Needs attention", under 50 "Needs work soon".
8. **No score** when no page could be opened ("couldn't verify" beats a guess). A partial report is scored on what was checked and says so.

**Same site, same score.** Timing-sensitive findings (Page Load Time, Largest Contentful Paint, Layout Shifts, Slow Server Response, Heavy Page, Many Requests, Oversized Images, and the two "check failed" notes) move with the network and our server's load. Every score also stores `value_without_timing`; two runs "score the same within the timing tolerance" when those agree (`report.scores_match`), and `timing_sensitive_points` says how much of the score is timing. The harness checks this on every run (target "score stability").

**Re-checks** store the previous score, show the change ("Up 8 points since your last check on Oct 3"), and say so when the formula or an area's `CHECK_VERSIONS` date changed in between — part of the difference may then come from GetBuggy, not the site. Bump an area's date in `report.CHECK_VERSIONS` whenever its checks change in a way that can change findings; bump `SCORE_FORMULA_VERSION` if any number above changes.

## Decisions

- **Rate limits and health-check timeout (2026-09-19, GetBuggy Step 3), decided autonomously — no explicit founder number given, picked conservatively for a free public tool with no login yet:** per-IP limit `5` runs/hour (`RATE_LIMIT_PER_IP_PER_HOUR`), daily global cap `200` browser runs (`DAILY_GLOBAL_RUN_CAP`), `/health`'s browser-launch-check timeout `20`s (`HEALTH_CHECK_TIMEOUT_SECONDS`). All three are env vars, not hardcoded — change on Render without a deploy once real usage data says otherwise. If 200/day feels wrong once there's real traffic (too tight for organic growth, or too loose for the cost budget), say so and it's a one-line env var change, not a code change.
- **Free tier checks 5 pages per crawl; Pro checks 10+ (2026-09-19).** Implemented: `core.py`'s `DEFAULT_CRAWL_PAGE_CAP` is `5`; the report's summary line (`summarize_site_check`) adds a one-line note — "Checking more pages is coming with Pro." — whenever a site had more pages than got checked, and says nothing extra when the whole site already fit under the cap. The cap stays fully configurable (`CRAWL_PAGE_CAP` env var, and the `page_cap` field `POST /api/check` already accepts) specifically so Pro can raise it later without a crawl-logic change. `CRAWL_TIMEOUT_SECONDS` (the flat 6-minute crawl budget) is unaffected by this — it's a promise about wait time, not tied to page count.
- **Cookie-compliance copy defaults to US, with a `jurisdiction` field.** When GetBuggy adds a cookie-consent/tracking-disclosure check, its plain-English copy defaults to US-style language (no cookie banner required) unless the report is tagged with a `jurisdiction` value of `eu_uk` or `both`, in which case EU/UK-style guidance (consent banner, no pre-consent non-essential cookies) is used instead. **Implemented in Step 7 (2026-10-11)**: `jurisdiction` on `POST /api/check` (default `us`; anything else is a plain-English 400), the form's "Where are most of your visitors?" select, `checker.py --jurisdiction`, and `run_site_check(jurisdiction=...)`. What it changes is listed in the Step 7 decisions below.
- **Report retention is 30 days.** A generated report (URL + findings + timestamp) is retained for 30 days, then deleted. `legal/privacy-policy.md` §5 now states this. **Implemented 2026-10-11 in MongoDB (Atlas on the live service), at the founders' request** (`report_store.py`): each finished report is saved as `{_id: job_id, url, result, created_at}` — no IP, nothing about the visitor — and a TTL index on `created_at` makes MongoDB delete it 30 days later by itself. `GET /api/check-status/{job_id}` falls back to the saved copy once the in-memory job is gone (pruned after 30 minutes, or a restart), and never serves one past 30 days even before the TTL sweep runs. Decided autonomously: (a) off unless `MONGODB_URI` is set, so local dev, CI and an unconfigured deploy behave exactly as before and nothing connects anywhere by default; (b) a database failure is logged (exception class only — never the URL or the URI, which holds the password) and never turns a finished report into an error; (c) 30 days is a constant, not an env var, because the privacy policy promises it; (d) lookup by job id only — no listing, no per-site history (that's Pro). Saved reports go through the same security-detail redaction as live ones (Step 5). The database user needs only `readWrite` on the `getbuggy` database, and Atlas's IP Access List should name Render's outbound IPs, not `0.0.0.0/0`.

- **Step 4 crawl decisions (2026-09-21), decided autonomously:**
  - *"partial: N of M"*: N = pages that finished, M = pages the crawl had selected to check (not the whole site's page count, which is reported separately as "found"). Pages that timed out loading count as attempted and are called out ("couldn't be opened"), never as checked.
  - *Primary nav* = links inside `<nav>`, `<header>` or `role=navigation` in the homepage's **rendered** DOM. Footer links don't count as nav.
  - *Priority words* (contact/pricing/book/order/shop) are matched against the URL path only.
  - *Sitemap findings are grouped* (one finding per kind, with examples) rather than one per URL; only the first 100 sitemap URLs are status-tested; sitemap children must be on the same site and pass the SSRF guard. A 404 is only reported after a second (GET) request agrees.
  - *"Another host"*: `www` vs apex is the same host; any other subdomain counts as another host. `http://` is flagged only when the site itself is `https://`.
  - *Redirect chains*: the cap of 5 applies to GetBuggy's own requests; page loads are measured after the fact (Chromium can't be capped) and 3+ hops are LOW.
  - *Static-vs-rendered links*: flagged LOW only when the page has 5+ rendered links (avoids noise on tiny pages) and under 20% exist in the server HTML.
  - *Soft 404*: fingerprint = words on the rendered page minus words that just echo the page's own URL; ≥90% word overlap with the site's answer to a made-up address flags a page (verified if identical, else needs_look). The homepage is never flagged.
  - *Bot-blocking*: a fixed list of domains that routinely block automated checks (Google, Amazon, Yelp, social platforms, …) is tolerated silently (noted under "couldn't check"). Any other 403/406/429 gets one real-browser retry, and a second failure is a LOW `needs_look` finding — never HIGH. Social profile links: HIGH only when both our request and the browser saw 404/410.
  - *`javascript:void(0)`*: MEDIUM but `needs_look` — we don't click links, so we can't know whether it opens a menu.
  - *Vague link text* includes bare URLs; an `aria-label` suppresses it.
  - *Concurrency*: left at 2 on Render (env var), code default 1. The "try 3 in local Docker" experiment was not run: Docker isn't installed on the dev machine and no browser-launch or concurrency change was made.
  - *Speed*: link probing parallelised (8 at a time) with a crawl-wide cache; `networkidle` waits are capped at 4 s.

- **Step 5 dedup/classification decisions (2026-09-21), decided autonomously — from cakesbody.com's first real ten-business-test report (382 "problems" on 5 pages):**
  - *Evidence-based dedup key*: `(category, evidence)`. A check gets an explicit `evidence` value when there's one concrete "thing" involved (a URL, an image src, a form's id/name, a page's exact bundled example set); everything else falls back to category-only, which is a deliberate choice — a generic per-page count (mobile text size, tap targets, heavy page, ...) is the same underlying issue wherever it recurs, so it collapses across every page it's found on, not just literal duplicates.
  - *Third-party rollup lives in `core.py` now, not the frontend* — the whole point was making the headline number honest, so it has to reflect the rollup too, not just the rendered cards.
  - *Missing Alt Text is bundled per page* (one finding listing every image, like Oversized Images already did), not per image — a product page with 30 unsplash-style photos was the single largest contributor to the original 382.
  - *JS-crash visible-break heuristic*: correlates "did anything else on this page load actually break" (Broken Form / Failed Network Request / Mobile Horizontal Scroll / a check that couldn't complete), not "did this specific error cause that specific breakage" — the latter isn't observable with what Playwright exposes. Documented as a heuristic, not a proof, in `_classify_js_errors`'s docstring.
  - *cakesbody.com's regression target checks a ceiling (`expected_max_unique_problems: 100`), not exact categories* — a live, complex, tracker-heavy store's exact per-category counts vary run to run for reasons outside this codebase (which tracker times out, whether the site's own sitemap.xml is discovered in time). The ceiling is the invariant that actually matters: never regress back toward one-problem-per-occurrence. Observed range across repeated post-fix runs: 40-61 unique problems.
  - *Sitemap-exclusion list is fixed, not configurable per-platform*: `/cart`, `/checkout`, `/account`, `/customer_authentication/*`, `/search`, `/collections/all`, any "login"/"logout" path segment, any URL with a query string. Chosen because these are Shopify conventions specifically (the platform the ten-business test's first site — and most early users — run on); revisit if a non-Shopify platform's own conventional "expected absent" pages turn out to differ.
  - *Dedup evidence must be a stable identity, never a positional artifact* (found testing site #2, lingcode.dev, 2026-09-25): a form with no `id`/`name` used to dedup by its display label ("#1" = "first form on this page"), which isn't stable across pages and silently merged different pages' distinct anonymous forms into one finding. Fixed by scoping that one fallback to the page URL. Standing rule going forward: any new `evidence` field must be checked against "is this actually the same identity everywhere it's reused, or just an artifact of how this one check happens to compute a label" before shipping — see the Progress Log entry for detail.

- **Step 5.3 decisions (2026-09-26), from a real founder-read report on heavenmayhem.com, decided autonomously:**
  - *"Utility page" is a distinct concept from "expected absent from sitemap," not the same list reused.* The sitemap-exclusion list also treats `/collections/all` and any URL with a query string as "expected absent" — correct for a sitemap (they're duplicate/paginated views), wrong for "should SEO/form checks run here" (both are still real, readable content). `core._is_utility_page` deliberately excludes both.
  - *LCP got Google's own published thresholds (2.5s/4.0s), not the founder's page-load numbers (3s/5s) reused.* The founder's fix request only named "total load" explicitly, but LCP had the exact same "meaningless ratio" problem and wasn't called out separately — extended anyway, since leaving it as-is would leave the same complaint live under a different finding name. Given a choice between inventing a third number scheme and using the metric's own industry-standard thresholds (already the precedent CLS sets in the same function), used Google's.
  - *A platform-domain form is skipped before any interaction, not excused after.* `action_domain` is now computed and checked at the very start of each form's loop iteration, before wizard-detection, filling, or clicking — a login form embedded by the platform is never touched at all, not filled-then-footnoted.

- **Step 5.4 product decision (2026-09-26): "Mobile Text Too Small" and "Mobile Tap Targets Too Small" removed entirely, not tuned.** Not a bug fix — a call about what the tool should even be checking. Small text and small tap targets on a brand site are usually a deliberate design choice, not a defect, and flagging them read as GetBuggy not understanding the business it's checking. `check_mobile_responsiveness`'s per-element text/tap-target scan was deleted, not just its findings suppressed — nothing computes or stores those counts anymore. `Mobile Horizontal Scroll` (a real, unambiguous layout break — content literally wider than the screen, never a design choice) stays untouched, as does the Step 5.3 load-time threshold rule (nothing under 3s, LOW 3-5s, MEDIUM over 5s) — both explicitly reaffirmed as correct in the same request, so no code change there, just no regression. This also retroactively closes the "mobile tap-target check over-counts on plain pages" Known Issue — moot once the check is gone, not tuned away.

- **Step 5.5 decisions (2026-09-26), the tenth and last ten-business-test site (housejanolo.com, Squarespace), decided autonomously:**
  - *A first-party 404 only earns HIGH/verified when the server probe AND a real-browser recheck independently agree.* Just requiring a browser recheck isn't enough on its own — if the recheck disagrees (loads fine) it's not broken at all (existing behavior, unchanged); if the ORIGINAL status wasn't already 404/410 (e.g. it was a bot-block code and only the recheck found 404), that's a weaker, single-method signal and stays at the existing MEDIUM/needs_look tier, same as before. Only true double-confirmation crosses to HIGH/verified — external/bot-blocked-domain links never do, regardless of how many checks agree, since there's no more-authoritative way to check a site we don't control.
  - *The www/apex/trailing-slash theory for the sitemap-homepage bug didn't hold up — investigated with the real site rather than assumed.* `page_key` already normalizes all three correctly; fetching housejanolo.com's actual sitemap.xml showed the real cause was Squarespace listing the homepage under an internal slug (`/home`), a genuinely different path. Chose not to special-case that slug (fragile, and wrong for the next platform's own alias scheme) — exempted the site root from the comparison entirely instead, since it doesn't need a sitemap entry to be findable.
  - *"Missing from sitemap" now depends on the crawl's own broken-link findings, so it moved out of `_site_findings` (which runs before any page is checked) into a new post-crawl step.* The tradeoff: this finding no longer appears in the progressive/streaming UI during a live crawl (the early `meta` payload doesn't have it), only in the final report — accepted, since correctness (never contradicting the broken-link finding) matters more than that one finding showing up a few seconds earlier.
  - *"Heavy Page" per-page entries carry their own byte count as `evidence`* (a deliberate, one-off exception to the usual "no evidence = category-only dedup" default) *specifically so a post-crawl step can compare pages and name the heaviest one*, then deletes the per-page entries — the same "compute after the crawl, once pages are known" pattern as the sitemap fix above, reused for a different reason (comparison, not cross-referencing).

- **Step 5 security decisions (2026-10-11, `06-step5-security.md`), decided autonomously:**
  - *"Every finding from this step carries `category: security`" is implemented as a separate field, `group: "security"`, not by overwriting `category`.* `category` is the stable name that dedup (`(category, evidence)`) and every regression baseline key on; setting it to the literal `"security"` would merge seven different exposed files into one finding and blind the harness. `group` is what the gate, the frontend badge and the harness filter read.
  - *Only real exposures are gated.* The endpoint table also contains site-hygiene items (robots.txt erroring, no sitemap, favicon, missing pages returning 200, plain server error page, www vs non-www, web manifest). Hiding "you have no sitemap" behind "verify you own this site" would make the security count meaningless and the free report worse, so those are ordinary public findings. Everything about transport, headers, secrets, exposed files, versions, third-party scripts and break-in signs is gated. **Founders: say so if you wanted literally everything gated.**
  - *Mixed content moved into the gated group* (split Active MEDIUM / Passive LOW, per the step). It used to be a public MEDIUM. Visitors can see it themselves, so this is the one gating call worth a second look.
  - *Missing security headers are one LOW finding listing the missing ones, not one finding per header.* The step says "each LOW"; severity is unchanged, but six separate findings would turn a typical small site's public card into "We found 9 possible security exposures" for what is one server-config fix.
  - *TLS 1.0/1.1 detection is not built.* It needs deliberate old-protocol handshakes, which aren't GET requests — outside CLAUDE.md's "the only active probes allowed are GET requests to a fixed endpoint list" — and modern OpenSSL builds often can't negotiate them anyway (results would be "couldn't verify" more than an answer). Every report says it wasn't checked.
  - *"Unregistered script domain" = DNS says the host doesn't exist (NXDOMAIN), reported HIGH but `needs_look`.* Proving a domain is unregistered needs a WHOIS/RDAP lookup at a third-party service with site-derived data; DNS alone is enough to say "this can't load and might be up for grabs."
  - *Third-party scripts over http:// are reported as Mixed Content (Active)* on an https page (the same fact, one finding); on an http-only site "Site Doesn't Use HTTPS" already covers it.
  - *WordPress core uses WordPress.org's own stable-check labels* (`insecure` → HIGH, `outdated` → MEDIUM). As of 2026-10-11 WordPress.org marks every version before 7.1.3 `insecure`, so any WordPress site not on the newest release gets a HIGH. That's WordPress.org's call, quoted, not ours. Plugin **vulnerability** data isn't bundled: Wordfence's free v2 feed now answers HTTP 410 and every other feed needs a key, so plugins are only compared against their latest release (MEDIUM, `needs_look`) and the report says plugin CVEs weren't checked. If the founders get a Wordfence/WPScan key, `update_security_data.py` is where it goes.
  - *wp-login.php / wp-admin/ are not probed.* No finding in the step depends on them, so probing them would be traffic for nothing.
  - *Probes run at most 4 at a time per site* (`MAX_PARALLEL_PROBES`) inside a 45-second site-pass budget; any probe that can't connect becomes a "couldn't check" note, never a silent pass.
  - *"Every probe logged" = a stderr line with method, path and status only* (`SECURITY_PROBE GET /.env -> 404`), keeping site URLs out of logs like the funnel rule; the full list (URL + status) is stored on the report under `security_details.probes`, which is gated.
  - *Compromise heuristics are deliberately strict*: "server HTML differs from rendered" only fires when the server-only text also contains spam words (app-style sites legitimately render very differently); scrambled-script needs execute + decode + a long encoded blob together; hidden spam links need two or more. All are `needs_look`.
  - *"Verify you own this site" has no verification flow behind it yet* — ownership verification is an accounts feature (Phase 2/Pro), out of scope. Until then the only way to see details is the server flag. Copy used verbatim from the step.

- **Step 6 accessibility decisions (2026-10-11, `07-step6-accessibility.md`), decided autonomously — full per-check reference in `CHECKS.md` "Accessibility (Step 6)":**
  - *axe-core 4.14.0 is vendored in `vendor/axe-core/`, not loaded from a CDN.* A check never depends on a CDN being up, and the exact ruleset a report used is pinned with the code. Byte-identical to the npm release (verified against npm's published integrity hash); MPL-2.0 licence kept alongside. Upgrading is a deliberate file swap plus a harness run, since new axe rules can move baselines.
  - *"WCAG 2.2 AA" = axe's WCAG 2.0/2.1/2.2 level A and AA tags, plus `heading-order` and `duplicate-id`/`duplicate-id-active` switched on by name.* axe files those three under best practice, so a tag-only run would never report two things the step names explicitly.
  - *Five axe rules are switched off, each because something else already covers it or it was deliberately removed:* `image-alt` (Missing Alt Text already reports it, bundled per page — no double count), `document-title` (Missing Page Title), `video-caption` and `no-autoplay-audio` (replaced by our own media check, which can tell a silent background loop from a real video), and `target-size` — small tap targets were removed as a finding in Step 5.4, and it's pinned off so an axe upgrade can't quietly bring it back.
  - *Severity: MEDIUM when it stops someone using the site (can't read it, can't fill a field, can't press a button, can't zoom), LOW for structure/code problems a screen reader mostly copes with, nothing HIGH.* The step only fixed severities for media (MEDIUM) and the statement (LOW). HIGH in GetBuggy means "broken for everyone"; a contrast or label problem is serious but isn't that. **Founders: say so if you want, e.g., unlabelled form fields on a contact form treated as HIGH.**
  - *Rules are grouped into 23 plain-English categories, one finding per category per page,* with element count, up to 3 examples in words a visitor would recognise (`"Order now" (button)`), and the rule IDs/selectors in brackets for the web person. A rule with no translation (a future axe addition) is reported at LOW in axe's own wording — never silently dropped.
  - *Only axe "violations" are requested, never "incomplete", so every axe finding is `verified`.* axe reports a violation only when the rule fully evaluated and failed; asking for its unsure results would add noise and slow every scan.
  - *Cross-page dedup evidence for an axe finding is the set of rules that fired.* Stable identity (passes the Step 5 "no positional artifacts" rule), and element counts are summed across pages. Known side effect: the same category can appear twice on a crawl report when different pages trip a different mix of its rules (e.g. `label` on one page, `label` + `select-name` on another). Left as is for now — collapsing to category-only evidence is a one-line change if the founders see it in a real report.
  - *Time budget is adaptive, not decided up front.* Every page is scanned until the first scan that's slower than `A11Y_SLOW_SCAN_SECONDS` (10s) or times out at `A11Y_SCAN_TIMEOUT_SECONDS` (20s); from then on the crawl scans only the homepage and pages whose path contains contact/book/appointment/reserv/schedul. Each skipped page and the site as a whole get a "couldn't check" note. Both are env vars, tunable on Render without a deploy. Measured on the seven baseline sites' homepages: axe 0.1–0.4s, focus check ≤0.9s — the fallback should rarely trigger. There's no separate on/off switch; the budget is the skip mechanism `CLAUDE.md` asks for.
  - *Keyboard focus visibility is tested by pressing Tab for real* (up to 20 stops) and comparing each focused element's look with how it looked unfocused, not by reading CSS rules. Always `needs_look`: a focus indicator drawn on a separate overlay element is invisible to this.
  - *Media:* autoplay with sound = MEDIUM `verified`; sound 3 seconds or shorter is exempt (WCAG 1.4.2's own exemption). Video without captions = MEDIUM `needs_look` (captions burned into the picture can't be detected). A muted, autoplaying, control-less video is treated as a background loop and not flagged — so WCAG 2.2.2 ("moving content needs a pause button") **is not checked**. Embedded YouTube/Vimeo/Wistia/Loom players can't be inspected and go under "couldn't check".
  - *Overlay widgets: AudioEye added to the three the step names; severity LOW + `needs_look`.* Detected by where any script, frame, stylesheet or loaded resource comes from. The message states plainly that an overlay doesn't make a site accessible or compliant.
  - *Accessibility statement: whole-site crawls only, `needs_look`.* Looks at every homepage link (text, `aria-label`, address — footer included) and the sitemap's paths for "accessib"/"a11y". `needs_look` because the statement could exist somewhere we don't look. Not run on a single-page check, which has no "site" to judge.
  - *Accessibility findings are public, not ownership-gated.* They're about what any visitor experiences, not exposures; Step 5's gate stays limited to security.
  - *All accessibility checks run on every page, utility pages included, and before the form check* — a login or cart page still has to be usable, and axe should see the page before test entries are typed in.
  - *The "automated checks catch only part of it" note is always shown* — on clean results too, and after every CLI report — next to a top-5 table (severity, then elements affected).
  - *Regression baselines:* nine crawl fixtures now expect "No Accessibility Statement" (none of them link one — a side effect of how they're built, commented as such), plus "Page Language Not Set" on `test_site_security` and "Page Refreshes or Redirects on a Timer" on `test_site_hacked`. New fixtures: `test_page_a11y.html` (11 planted violations plus controls that must stay quiet) and `test_site_a11y/` (time-budget fallback and statement found). `--skip-live` harness: 17/17. The live `medvi.org` baseline has no accessibility expectations yet — to set from its next scheduled/manual run, not guessed.

- **Step 7 cookie and consent decisions (2026-10-11, `08-step7-cookies.md`), decided autonomously — full per-check reference in `CHECKS.md` "Cookies and consent (Step 7)":**
  - *What `jurisdiction` changes.* `us` (default): "tracking with no banner" fires **only when an advertising tracker loads** (US state laws' opt-out of "sale/sharing"; plain analytics with no banner isn't a US finding), and "tracking before consent" and "reject harder than accept" don't show at all — the US model is opt-out, so neither is the issue there. `eu_uk`: all three show, worded around GDPR/ePrivacy/PECR. `both`: the EU/UK wording plus a sentence on US opt-out rules. The phone-screen, privacy-policy and cookie-setting findings show for every jurisdiction. **Founders: say so if you wanted the US default to flag analytics-without-banner too, or to show the two EU-only findings with US wording.**
  - *The consent findings are judged on the homepage only, from one fresh visit with nothing clicked* — the page every banner has to work on, and "before any user interaction" can only be guaranteed on a visit nobody has touched. The cookie list in the report covers every page checked: each page snapshots its own cookies and requests right after it loads, before any other check touches it.
  - *We never click the banner.* So "tracking before consent" is directly observed (`verified`), but whether Accept/Reject actually work isn't tested — that would be an interaction, and the rules only allow observing.
  - *"Tracking" = analytics or advertising, per the bundled list.* Tag managers, fonts, CDNs, payment and consent tools are `functional`; anything not on the list is "unknown" and never counts as tracking — the report would rather miss a tracker than call a font CDN one. Google Consent Mode's "consent denied" pings (`gcs=G100`) don't count as tracking — that's how the tool is designed to work before consent.
  - *A consent tool installed but no banner shown to us → "couldn't check", not a finding.* Render is in the US and the check is an automated browser; geo-targeted or bot-hidden banners are normal, so saying "you have no banner" would be a guess.
  - *Cookie flags (Secure / HttpOnly / SameSite) are security findings, ownership-gated like Step 5*, one finding per kind naming the cookies (same reasoning as Step 5's "one finding for missing headers"). They're read from the site's **own** `Set-Cookie` headers only — a tracker's script-set cookies aren't the owner's to change — and skipped on Shopify, Wix, Squarespace and Webflow (the platform sets them; noted under "couldn't check"). "Secure" is only judged on `https://` sites. "Auth-looking" is by name (sess/session/auth/token/login/jwt/sid…, never csrf/xsrf), so that one is `needs_look`.
  - *Privacy policy severities the step left open:* placeholder = same as missing (MEDIUM with tracking, else LOW); missing with no tracking = LOW; not in the footer, undated, or older than ~2 years (730 + 60 days) = LOW. A partial date ("July 2024", or just a year after "updated") counts as the end of that period — benefit of the doubt to the site. The tracker-mismatch check is lenient ("Google" anywhere counts for Google Analytics) and gives **one** finding naming every unmentioned company.
  - *The policy page is opened in the browser* (policies from Termly/Iubenda are often drawn by script), through the SSRF guard, even when it's hosted on another domain.
  - *"Reject not as easy as accept" = the banner's first screen has an accept-type button and no reject-type button*, judged by wording. Size and colour aren't compared. *"Blocks the phone screen" = the banner covers ≥90% of a 390×844 screen, can't be scrolled, and no accept/reject/close button is fully on screen.* The phone visit only happens when the desktop visit saw a banner (saves a page load on most sites).
  - *Time:* page loads in this pass are capped at 30s each inside a 75s budget for the whole pass, run once per crawl alongside the security pass; anything that doesn't fit goes under "couldn't check". `GETBUGGY_SKIP_COOKIE_CHECKS=true` switches the pass off (the report says so) — the skip switch `CLAUDE.md` asks for.
  - *Harness:* cookie findings carry `topic: "cookies"` and are compared only on targets that opt in with `expected_cookie_categories` (like security) — live sites' trackers change on their owners' schedule, and every older fixture would otherwise pick up "No Privacy Policy Found". No existing baseline changed. Fixtures reach a stand-in "tracker" on `localhost` (same server, different host from the site's `127.0.0.1`), mapped to a real company only while `GETBUGGY_TEST_TRACKER_ALIAS` is set — no real tracker is ever contacted.

- **Step 8 report decisions (2026-10-11, `09-step8-scoring-report.md`), decided autonomously:**
  - *Points 15 / 5 / 1, cap 25 per area.* One HIGH puts a site at 85 ("A few things to fix"); a broken form plus a broken internal link is 70 ("Needs attention"). LOW is 1 so ten polish items cost less than one real breakage. **Founders: these numbers are a judgment call — say if a single HIGH should hurt more.**
  - *Security findings count toward the public score, and the public "by area" list shows the security area's count and points* (e.g. "Security: 2 possible exposures found", −20 in "How this score is worked out"). That's category-level — no titles, files or pages — but the points do hint at the severity mix. Leaving security out of the score would make an exposed `.env` invisible to the number owners will look at first. **Founders: say so if the public score should exclude security, or hide its points.**
  - *No new severity assignments.* The rubric describes what the existing per-check severities already mean; no check's severity changed in this step, so no baseline moved.
  - *The finding schema is added by `report.finalize_report` when a report is finished*, not by rewriting every check: `title` = the category name; `why_it_matters` / `how_to_fix` / `who_fixes` come from `finding_guide.GUIDE` (one row per category, accessibility rows taken from `checks_accessibility`'s own table); `id` = hash of category + evidence (the dedup identity, stable across runs); `pages` = every page it was found on (`[]` = whole site); `evidence` masked with the Step 5 secret patterns and capped at 300 characters; `check_version` = `<area>/<date>` from `report.CHECK_VERSIONS`; `platform_note` only for hosted platforms (Shopify/Wix/Squarespace/Webflow) and WordPress server settings, and only says who runs the server — never a menu path we haven't verified. `message` stays as the "what's wrong on this site" text. A category with no guide row gets generic severity-based wording rather than nothing; a unit test fails if any category in the six pre-Step-7 check modules lacks a row. Step 7's cookie categories don't have rows yet (generic wording until they do).
  - *A page that couldn't be opened makes the report partial* (`partial_reason: "pages_failed"`), alongside Step 4's `time_cap` and `worker_stopped`. Every partial report carries `not_completed`, a plain-English list of what it didn't get to. *"Never a bare error if any check finished" now includes the site-wide checks*: a worker that dies after discovery, or whose final line is unreadable, returns a partial report with the site-wide findings (and no score) instead of an error.
  - *The queue is in-memory and FIFO, capped at `MAX_QUEUE_LENGTH` (env var, default 10)*; past that the visitor gets a plain-English "very busy" message. The wait estimate is `ceil(position / MAX_CONCURRENT_CHECKS) × the average of the last 20 crawl times` (120 s until there are any), shown in whole minutes. A queued check counts against the rate limits when it's accepted, not when it starts. Abandoned queued checks still run (their reports stay reachable by permalink) — not worth the complexity of liveness tracking at this size.
  - *Permalinks use their own random token* (`secrets.token_urlsafe(16)`, 128 bits) at `/r/<report_id>`, separate from the job id. The job id still unlocks `/api/check-status`, which shows security details when `GETBUGGY_SHOW_SECURITY_DETAILS=true`; if the share link reused it, sharing would leak them. `/api/report/<id>` and the export are always gated, whatever the flag. Malformed ids are rejected before any database lookup.
  - *Permalinks last 30 days only where `MONGODB_URI` is set*; without a database they last as long as the in-memory job (30 minutes, or until a restart), and an expired link says plainly that reports are deleted after 30 days. Not adding a second, file-based store: Render's disk is wiped on deploy and LingCode's hosted tier is read-only.
  - *The deletion job* is `report_store.purge_expired()`: run by the server at startup and every `REPORT_PURGE_INTERVAL_SECONDS` (default 3600), and by hand with `python report_store.py purge`. It sits alongside MongoDB's TTL index (which stays), so deletion never depends on one mechanism, and reads never serve anything past 30 days in between. It also drops finished in-memory jobs past 30 minutes.
  - *Re-check deltas need no history or cookies*: the page sends the permalink id of the report it last showed (`previous_report_id`), and the server uses it only if that report is for the same site (www = apex). "Check this site again" pre-fills the address; the visitor still ticks the authorisation box.
  - *The export is markdown that reads fine as plain text* (simple headings, "What's wrong / Why it matters / How to fix it / Who fixes it" lines, up to 5 pages per finding), with the permalink, the score, the by-area list, the security count only, what couldn't be checked, and the accessibility and 30-day notes. `python checker.py --crawl --markdown <url>` prints the same thing.
  - *Clean lines say "on the pages we checked"* for every page-based area, and an area whose checks didn't run says "We couldn't check this" instead (no page opened, or security checks switched off) — never a clean line for something we didn't look at.
